# School ERP — Project Guide

## What this is

A multi-school ERP for Nursery–Class 10 schools, with four roles: **Super Admin**, **Admin**, **Faculty**, **Parent**. Next.js (App Router) + TypeScript + Tailwind + Firebase (Auth, Firestore, Storage) + one server-side API route (Firebase Admin SDK).

The full functional spec lives in [docs/context.md](docs/context.md) — treat it as the source of truth for *what* every module should do. This file describes *where the project currently stands* against that spec, *what's known to be broken or unreconciled*, and *what to build next*.

## Current state (built and working)

- **Auth + role routing**: [context/AuthContext.tsx](context/AuthContext.tsx) listens to Firebase Auth, loads the `users/{uid}` Firestore doc for role/schoolId. [app/login/page.tsx](app/login/page.tsx) signs in and redirects via `ROLE_HOME` ([lib/roles.ts](lib/roles.ts)) — `parent` now lands on `/parent/profile`, not a dashboard stub. [components/RoleGuard.tsx](components/RoleGuard.tsx) client-side-guards each role's route group.
- **Super Admin module** — schools ([lib/schools.ts](lib/schools.ts), `app/superadmin/schools`), admin logins ([lib/admins.ts](lib/admins.ts), `app/superadmin/admins`), dashboard, profile. Unchanged since the project's start.
- **Admin · Faculty module** ([lib/faculty.ts](lib/faculty.ts), [app/admin/faculty/page.tsx](app/admin/faculty/page.tsx)) — full Add/Edit/Delete/Search, photo upload, Firebase Auth login creation via the secondary-app pattern in [lib/secondaryAuth.ts](lib/secondaryAuth.ts). Deleting a faculty member now also deletes their Auth account (see "Account deletion" below).
- **Admin · Classes & Sections module** ([lib/classSections.ts](lib/classSections.ts), [components/ClassSectionsManager.tsx](components/ClassSectionsManager.tsx), `app/admin/classes/*`) — Admin picks a class (fixed list in [lib/classes.ts](lib/classes.ts)), adds sections, and assigns one faculty member as `classTeacherUid` per section (a faculty can be class teacher of only one section at a time). This is the **real, populated** source of "who teaches which class" — see the Faculty/FacultyProfile note below for what it replaced.
- **Class Teacher · Student Directory** ([lib/students.ts](lib/students.ts), [app/faculty/class/[classId]/students/page.tsx](app/faculty/class/[classId]/students/page.tsx)) — a class teacher's own class/section is resolved automatically from `classSections.classTeacherUid` (no manual picker; if unassigned, the page shows an empty state telling them to ask their Admin). Add/Edit/Delete/Search students. Student ID is entered manually by the class teacher (not auto-generated). One login is created per student ("Student Login", used by whichever parent signs in) — not one login per guardian. Father/Mother/Guardian are plain data fields (name, phone, occupation only — no per-parent Aadhaar/email), independent of the login. Digital ID is a photo/PDF upload, not a generated code.
- **Parent · Profile** ([app/parent/profile/page.tsx](app/parent/profile/page.tsx)) — reads the student where `guardianUids array-contains` the signed-in parent's uid (enforced by `firestore.rules`, not just hidden in the UI) and shows everything read-only. Attendance/Transport sections are explicit "Not available yet" placeholders, not faked data.
- **Admin · Subjects module** ([lib/subjects.ts](lib/subjects.ts), `app/admin/subjects/page.tsx`) — per-class subject catalog (Nursery–Class 10), shared across all sections of a class (not section-specific): Name, Code, Type (Theory/Practical/Activity), Hours/Week. Add/Edit/Delete via one modal, class picked via a dropdown on the page itself (not a drill-down route, unlike Classes & Sections).
- **Admin · Timetable module** ([lib/timetableConfig.ts](lib/timetableConfig.ts), [lib/timetableGrid.ts](lib/timetableGrid.ts), [components/PeriodsEditor.tsx](components/PeriodsEditor.tsx), [components/ClassSectionsView.tsx](components/ClassSectionsView.tsx), [components/TimetableGridEditor.tsx](components/TimetableGridEditor.tsx), `app/admin/timetable/*`) — a manual grid editor (define periods once per school, then per class → section → day/period grid), **not** the Excel-upload design from `docs/context.md` Tab 3 (see "Two Timetable designs" below — still unreconciled). Sections now come from the real `classSections` collection (see next bullet) — the module no longer has its own section CRUD; picking a class here just lists that class's existing sections and links into the grid editor.
- **Account deletion / Auth cleanup** ([app/api/delete-account/route.ts](app/api/delete-account/route.ts), [lib/firebaseAdmin.ts](lib/firebaseAdmin.ts)) — the only server-side code in the app. Deleting a faculty or student now also deletes the associated Firebase Auth account(s) via the Admin SDK (the client SDK can only delete `auth.currentUser`, not an arbitrary uid), so the email becomes reusable. **Requires `FIREBASE_SERVICE_ACCOUNT_KEY` in `.env.local`** (a service account JSON, minified to one line) — not yet set as of this writing; until it is, Firestore docs delete fine but the Auth account is orphaned and a "email already in use" error will resurface on recreation.
- **Data model** ([lib/types.ts](lib/types.ts)) and **Firestore rules** ([firestore.rules](firestore.rules)) — designed up front for every collection in `docs/context.md`, and now partially superseded by what was actually built (see "Known debts" below). Two extensible "bucket" registries (`isSchoolScopedAdminCollection`, `isParentReviewedRequestCollection`) let a new collection get correct rules just by being added to a list — prefer that over a new `match` block when a collection fits either shape.
- **Everything else is still an empty placeholder**: Faculty Dashboard, all other Class Teacher modules (Attendance, Assignments, Achievements, Parent Requests, Leaves, Messages, Announcements), all Subject Teacher modules, Admin Transport/Fees/Circulars/Events, and every Parent page except Profile are 5–10 line stubs rendering `<EmptyState title="..." />` ([components/EmptyState.tsx](components/EmptyState.tsx)).

## Known debts / things to reconcile before building on top of them

- **`Faculty` vs `FacultyProfile` in `lib/types.ts`** — two competing Faculty schemas exist from an early merge. `Faculty` is the one actually used everywhere (`lib/faculty.ts`, the Admin Faculty page). `FacultyProfile` (with a `classSectionRoles` map) is dead — nothing writes it, and nothing in `firestore.rules` reads it anymore either (see next point) — it's pure unused scaffolding at this point, safe to delete once nothing else is expected to need it.
- **Two parallel Timetable *storage* designs still coexist** (this is narrower than it used to be — see "Fixed this pass" below for the sections part that got resolved), per the comment in `firestore.rules` right above the `timetableConfigs`/`timetableGrids` rules: the built grid-editor module, and the original `timetables/{classSectionId}` Excel-upload design from `docs/context.md` Tab 3 (schema exists in `lib/types.ts`, rules exist, nothing built). **Pick one before building any Faculty/Parent read view of timetable data** — right now neither Faculty nor Parent can see a timetable anywhere.
- **`firestore.rules` requires manual re-publish** — Firebase Console → Firestore Database → Rules → Publish. There's no CI/CD for this repo. This has caused real "why can't I save" confusion multiple times this session; always the first thing to check after any local `firestore.rules` edit — **including the rules cleanup below, which hasn't been published yet.**
- **`storage.rules` still doesn't match what `lib/students.ts` uploads to — known bug, deliberately not fixed**: the student photo/documents rule only allows `isAdminOfSchool()` or `isGuardianOfStudent()` to write, so a class teacher (faculty) attaching a photo on Add Student will get denied by Storage. A fix was written and then intentionally reverted — `storage.rules` is out of scope for now (only `firestore.rules` is being maintained/published). If Storage-backed uploads (student photo, Digital ID, faculty photo) ever need to work for a class teacher, `storage.rules` needs its own pass — see git history around this note for the fix that was reverted, it can be reapplied as-is. `lib/students.ts`'s `uploadStudentDigitalId` does write under the `students/{id}/` prefix (not a separate mismatched path), so it's at least denied for the same reason as the photo, not for a second unrelated reason.

### Fixed this pass (`firestore.rules` only)

- **Every `isClassTeacherOf()`/`isAnyTeacherOf()` call site was silently broken**, not just the one on `students/{id}` fixed earlier — it read a `classSectionRoles` map off the faculty doc that nothing has ever written, so it evaluated to `false` for every real faculty account. This affected `attendance`, `assignments`, `achievements`, `assessments`, `conversations`, `announcements`, `documents`, `parentClassLinks`, and `timetables/{classSectionId}` — i.e. every module still to be built in the "Flow to be executed" list below. Both helpers now resolve through `classSections/{id}.classTeacherUid` (`isClassTeacherOf`) or "any faculty of that class-section's school" as an interim stand-in for Subject Teacher (`isAnyTeacherOf`, until real per-subject assignment data exists) — the same fix already applied to `students/{id}`, now applied uniformly so the next module built on top of these rules won't hit the same wall. Also dropped the dead `classSectionRoles` comparison from `faculty/{uid}`'s self-update rule.

### Fixed this pass — the actual "Add/Edit Student silently doesn't save" bug (`lib/students.ts`)

This was **not** a rules-publish issue (confirmed rules were published) and not a code exception being swallowed — it's a Firestore-specific gotcha worth remembering: **Firestore validates a `list`/collection query against its entire potential result set, not its actual results — if the security rule can't be statically proven true for every document the query's `where` clauses could match, the whole query is rejected outright**, even when every real matching document would individually pass. `assertAdmissionNoAvailable` (the Student ID uniqueness check called by both `createStudent` and `updateStudent`) queried `students` filtered only by `schoolId` + `admissionNo`. The `list` rule's faculty branch is `isAnyTeacherOf(resource.data.classSectionId)` — since `classSectionId` wasn't part of the query's filters, Firestore couldn't bind it to prove the rule safe, and denied the query for every class teacher, every time, regardless of what was actually in the collection. Fixed by also filtering on `classSectionId` (now `assertAdmissionNoAvailable(schoolId, classSectionId, admissionNo, excludeStudentId?)`), the same filter shape `subscribeToStudentsForClass` already used successfully. Trade-off: Student ID is now only guaranteed unique within a class-section, not school-wide. **If you write a new Firestore query anywhere in this app, make sure every field the applicable security-rule branch depends on is also pinned by an equality filter in the query** — this class of bug won't throw anywhere obvious in dev, it just makes the request hang/fail with a permission error that's easy to misattribute to "rules not published."

### Fixed this pass — every `delete` in `firestore.rules` was silently denied (`firestore.rules`)

Another Firestore-specific gotcha, distinct from the two above: **`request.resource` is `null` on a `delete` operation** — there's no new document being written, so nothing to hold it. Every rule written as `allow create, update, delete: if ... request.resource.data...` (or `allow write: if ... request.resource.data...`, which covers delete too) works fine for create/update but **always throws/denies on delete**, since it evaluates `.data` on `null`. This exact pattern was present on 9 collections: the `isSchoolScopedAdminCollection` bucket (circulars, events, activities, transportBuses, feeStructures, classSections, facultyAssignments), `faculty/{uid}`, `parentClassLinks/{id}`, `attendance`, `assignments`, `achievements`, `assessments`, `announcements`, `timetables/{classSectionId}`, and `studentFees/{studentId}` — i.e. deleting a faculty member or a class section (the two delete features actually wired up in the UI) was completely broken, and every future delete feature built the same way would have hit it too. Fixed by splitting every one of these into a separate `allow create, update: if ... request.resource.data...` and `allow delete: if ... resource.data...` (the *existing* document, which — unlike `request.resource` — is always available on delete). **Rule of thumb: `delete` rules must always read `resource.data`, never `request.resource.data`.**

### Fixed this pass — resolved the "two parallel sections systems" debt (Timetable module)

The Timetable module (`ClassSectionsView.tsx`) had its own "Add Section" flow writing to a separate `timetableSections` collection, independent of the real `classSections` collection Admin · Classes manages — the exact duplication flagged above as debt. Per explicit instruction, removed "Add Section" (and its now-pointless "Delete") from the Timetable module entirely; it now reads sections straight from `classSections` via the existing `subscribeToClassSections`, and links into the grid editor using real `classSections` doc ids. `lib/timetableSections.ts`, the `TimetableSection` type, and the `timetableSections/{id}` rules block are all deleted — nothing referenced them anymore. `TimetableGridEditor.tsx`'s section-name lookup now uses the new `getClassSection()` (`lib/classSections.ts`) instead of the deleted `getSection()`. **Section creation/deletion now happens in exactly one place app-wide: Admin · Classes.** (README.md's Firestore-rules section was also a long-stale hand-copied snippet, still referencing `timetableSections` among other things missing dozens of collections — replaced with a pointer to `firestore.rules` as the single source of truth, rather than maintaining two copies.)

## Flow to be executed (build order)

Remaining work, in dependency order:

1. **Re-publish `firestore.rules`** in Firebase Console — just edited locally (see "Fixed this pass" above) and not live yet. (`storage.rules` is intentionally not part of this — see "Known debts".)
2. **Faculty Dashboard** (`app/faculty/dashboard`) — welcome section, summary cards, "My Assigned Classes" (now resolvable via `classSections.classTeacherUid`, same pattern the Student Directory page already uses), recent activity, notifications.
3. **Remaining Class Teacher modules** (`app/faculty/class/[classId]/*`, all stubs): Attendance, Assignments, Achievements, Parent Requests, Leave Management, Parent Communication, Announcements. Each should resolve "my class" the same way the Student Directory page does — don't reintroduce a manual class picker.
4. **Subject Teacher modules** (`app/faculty/subject/[classId]/*`) — blocked on deciding how subject-teacher assignment is tracked at all; nothing currently records which faculty teaches which subject in which section (the new Admin · Subjects catalog records *what* subjects a class has, not *who* teaches them).
5. **Resolve the remaining Timetable storage-design duplication** (grid-editor vs. `timetables/{classSectionId}` Excel design — sections themselves are already unified, see "Fixed this pass"), then give Faculty/Parent a read view of it.
6. **Admin · Transport, Fee Particulars, Circulars, Events** — the remaining stubs from `docs/context.md` Tabs 2, 4, 5, 6.
7. **Parent Dashboard**, remaining pages (`app/parent/*` besides Profile) — Academics, Assignments, Activities, Achievements, Attendance, Fee Particulars, Leaves (parent can create), Circulars, Document Upload (parent can create). **Transport GPS Tracking** and **Route Map** stay `EmptyState` per spec — explicitly deferred.
8. **Faculty common modules**: Circulars (view-only), Events (view-only), My Profile (change password, update photo).
9. **Set `FIREBASE_SERVICE_ACCOUNT_KEY`** so Auth-account cleanup on delete actually works end-to-end (currently unset).

## Conventions to follow

- New Firestore collection: add its shape to [lib/types.ts](lib/types.ts), add its rule via the appropriate registry in [firestore.rules](firestore.rules) (or a new `match` block only if neither bucket fits), then add a `lib/<name>.ts` with the CRUD functions.
- A faculty member's "own class" is resolved via `subscribeToClassSectionForTeacher` (`lib/classSections.ts`) — a live query on `classSections` for `classTeacherUid == currentUid` — not a URL param, not `classSectionRoles`. Every new Class Teacher module should follow this same pattern.
- Keep using `schoolId` scoping on every school-owned document, and `classSectionId` scoping wherever context.md describes class-level access.
- Parent → student linkage is solely `guardianUids` on the student doc; parent → class-level (non-student-scoped) reads go through the `parentClassLinks` marker doc, not a query on students.
- Deleting anything that owns a Firebase Auth login (faculty, a student's parent login) must also call `deleteAuthAccount` (`lib/secondaryAuth.ts`, hits `/api/delete-account`) — otherwise the email is orphaned and can never be reused, exactly the bug this was built to fix.
- Follow the existing page shell pattern (`components/Sidebar.tsx`, `components/Topbar.tsx`, `components/Modal.tsx`, `components/PageHeader.tsx`, `components/StatCard.tsx`, `components/DashboardCard.tsx`) already used throughout Admin/Faculty/Parent pages, for visual/UX consistency. `TopNav.tsx` no longer exists — all four roles use `Sidebar` now.
