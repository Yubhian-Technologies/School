# School ERP — Project Guide

## What this is

A multi-school ERP for Nursery–Class 10 schools, with four roles: **Super Admin**, **Admin**, **Faculty**, **Parent**. Next.js (App Router) + TypeScript + Tailwind CSS v4 + Firebase (Auth, Firestore, Storage) + one server-side API route (Firebase Admin SDK).

The full functional spec lives in [docs/context.md](docs/context.md) — treat it as the source of truth for *what* every module should eventually do. This file describes *where the project currently stands* against that spec: what's actually built and working end-to-end, what's a placeholder, how the whole app fits together, and what's known to be broken or unreconciled.

## Tech stack & architecture

- **Next.js App Router**, one route tree per role under `app/{superadmin,admin,faculty,parent}/*`, plus `app/login` and one API route (`app/api/delete-account`).
- **Firebase Auth** for login (email/password only — no self-registration; every account is created *for* someone by a higher role).
- **Firestore** for all app data, access controlled entirely by [firestore.rules](firestore.rules) (client SDK talks to Firestore directly — no data ever passes through the Next.js server, except the one delete-account route).
- **Firebase Storage** for uploaded files (photos, Digital ID docs), controlled by [storage.rules](storage.rules) — a **completely separate file with its own separate publish step** in Firebase Console from `firestore.rules` (see "Known debts").
- **Firebase Admin SDK**, server-only, used by exactly one route ([app/api/delete-account/route.ts](app/api/delete-account/route.ts)) to delete an arbitrary user's Auth account — the client SDK can only ever delete `auth.currentUser`.
- No other backend. No CI/CD — both `firestore.rules` and `storage.rules` are hand-published in Firebase Console after every edit.

## Auth & role-routing workflow (applies to every role)

1. [app/login/page.tsx](app/login/page.tsx) — a single login form (email + password) for all four roles. On success, it reads the signed-in user's `users/{uid}` Firestore doc to get their `role`, then redirects via `ROLE_HOME[role]` ([lib/roles.ts](lib/roles.ts)):
   - `superadmin` → `/superadmin/dashboard`
   - `admin` → `/admin/dashboard`
   - `faculty` → `/faculty/dashboard`
   - `parent` → `/parent/profile` (parents have no dashboard stub — Profile *is* their landing page, per spec)
2. [context/AuthContext.tsx](context/AuthContext.tsx) — app-wide, listens to `onAuthStateChanged`; whenever the Firebase Auth user changes, it fetches `users/{uid}` and exposes `{ user, profile, loading, logout, refreshProfile }` via `useAuth()`. Every page that needs the current user's `schoolId`/`role`/`name` reads it from here, not from Firebase Auth directly (the Auth user object has none of that — it all lives in the Firestore profile doc).
3. [components/RoleGuard.tsx](components/RoleGuard.tsx) — wraps each role's route group (`app/{role}/layout.tsx`, all `"use client"`), client-side redirects away if `profile.role` doesn't match the route's role, or if not signed in at all.
4. Every role's shell uses the same components for visual consistency: [components/Sidebar.tsx](components/Sidebar.tsx) (grouped nav from [lib/navigation.ts](lib/navigation.ts) — `SUPERADMIN_NAV` / `ADMIN_NAV` / `FACULTY_NAV` / `PARENT_NAV`), [components/Topbar.tsx](components/Topbar.tsx), [components/PageHeader.tsx](components/PageHeader.tsx), [components/StatCard.tsx](components/StatCard.tsx), [components/DashboardCard.tsx](components/DashboardCard.tsx), [components/Modal.tsx](components/Modal.tsx). `TopNav.tsx` no longer exists — all four roles use `Sidebar`.

**Accounts are created top-down, never self-registered:**
- Super Admin creates Admin logins (`app/superadmin/admins`).
- Admin creates Faculty logins (`app/admin/faculty`).
- A Class Teacher (Faculty) creates a Student + one Parent login together, as part of Add Student (`app/faculty/class/[classId]/students`) — see below.

## Role-by-role: what's built and how it works

### Super Admin — unchanged since project start, fully working
- **Schools** ([lib/schools.ts](lib/schools.ts), `app/superadmin/schools`) — Add/Edit/Delete schools (`name`, `place`). Every other role's data is scoped under a `schoolId`, so this is the root of the multi-tenancy model.
- **Admins** ([lib/admins.ts](lib/admins.ts), `app/superadmin/admins`) — creates an Admin login for a chosen school (email/password via the secondary-app pattern, see below), Edit/Delete.
- Dashboard + Profile pages, both simple/working.

### Admin — fully working for Faculty, Classes, Subjects, Timetable; Transport/Fees/Circulars/Events still stubs
- **Faculty** ([lib/faculty.ts](lib/faculty.ts), [app/admin/faculty/page.tsx](app/admin/faculty/page.tsx)) — full Add/Edit/Delete/Search/View. Fields: photo, name, gender, DOB, mobile, email, qualification, subjects (free text), designation, date of joining, prior experience + previous school, address, emergency contact, status (Active/Inactive). Creating a faculty member creates a real Firebase Auth login (email + password) via `createAuthUserAndRun` ([lib/secondaryAuth.ts](lib/secondaryAuth.ts)) plus a `users/{uid}` doc (`role: "faculty"`) and a `faculty/{uid}` profile doc. Deleting a faculty member deletes both Firestore docs **and** their Auth account (see "Account deletion" below), so the email becomes reusable.
- **Classes & Sections** ([lib/classSections.ts](lib/classSections.ts), [components/ClassSectionsManager.tsx](components/ClassSectionsManager.tsx), `app/admin/classes/*`) — Admin picks a class from a fixed Nursery→Class 10 list ([lib/classes.ts](lib/classes.ts)), adds one or more sections to it (e.g. "A", "B"), and assigns **one faculty member as `classTeacherUid`** per section — a faculty can be class teacher of only one section at a time (`assertTeacherAvailable` enforces this both on create and on reassignment). **This is the single, real, populated source of "who teaches which class" app-wide** — every other module (Student Directory, Timetable, Faculty Dashboard) resolves "my class" from `classSections.classTeacherUid`, never from a manual picker or URL param. Deleting a section also deletes its `timetableGrids/{id}` doc.
- **Subjects** ([lib/subjects.ts](lib/subjects.ts), `app/admin/subjects/page.tsx`) — a per-class subject catalog (Nursery–Class 10), shared across all sections of a class (a subject isn't section-specific — all of Class 5-A/B/C study the same subjects). Fields: Name, Code, Type (Theory/Practical/Activity), Hours/Week. Add/Edit/Delete via one modal; class picked via a dropdown on the page itself.
- **Timetable** ([lib/timetableGrid.ts](lib/timetableGrid.ts), [lib/timetableCellColors.ts](lib/timetableCellColors.ts), `components/timetable/*`, `app/admin/timetable/*`) — per-section, not shared: every `classSections/{id}` owns one independent `timetableGrids/{id}` doc (own days/periods/breaks/cells, `draft`/`published` status). Clicking "Create Timetable" auto-generates a default Mon–Sat × Period 1–8 grid with a Lunch Break rather than starting blank; "Edit Structure" customizes days/periods/breaks after. Cells hold subject/faculty/room/notes/color, edited via a dialog. A timetable must be explicitly **published** before Faculty/Parent can see it. Sections are read straight from the real `classSections` collection (no separate section-picker collection).
- **Subject Teacher assignment** ([lib/facultyAssignments.ts](lib/facultyAssignments.ts), [components/FacultySubjectAssignments.tsx](components/FacultySubjectAssignments.tsx)) — surfaced from the **Faculty page**, not Classes & Sections: a "Subjects" action on each faculty row (also in the View Faculty modal) opens a per-faculty modal where the Admin picks Class → Section → Subject and adds it to that faculty's list of assignments (with a list of their current ones, each removable). Writes `facultyAssignments/{classSectionId}_{subjectId}` docs (`role: "SUBJECT_TEACHER"`) — the real, populated source of "who teaches what where" for Subject Teachers, the counterpart to `classSections.classTeacherUid` for Class Teachers, and what filters which classes a Subject Teacher can post Assignments for (see below). Deliberately keyed from the faculty side (not the section side) — picking a faculty member first, then their classes/subjects, was the requested flow.
- **Transport, Fees, Circulars, Events** — `app/admin/{transport,fees,circulars,events}/page.tsx` are all 5-line `<EmptyState>` stubs. Nothing built yet.

### Faculty — Dashboard, Timetable, and the Class Teacher "Students" module are real; every other Class/Subject Teacher module is a stub
- **Dashboard** ([app/faculty/dashboard/page.tsx](app/faculty/dashboard/page.tsx)) — welcome header, stat cards (own class + student count, resolved live via `subscribeToClassSectionForTeacher`), and grouped quick-link cards for every Class Teacher / Subject Teacher / General module (most of which route through to stubs today, but the dashboard itself is complete).
- **Timetable** (`app/faculty/timetable/*`) — a real, read-only view of a section's *published* `timetableGrids` doc. Faculty browse to their own class-teacher section or any other section within the school; drafts are invisible to them (enforced by `firestore.rules`, not just hidden in the UI). Also includes **"My Timetable"** ([components/timetable/MyFacultyTimetable.tsx](components/timetable/MyFacultyTimetable.tsx)) — every period this faculty member is assigned to (as the cell's `facultyId`) across *all* published sections/classes in the school, merged and sorted in time order using each period's optional `startTime`/`endTime` (`lib/timetableGrid.ts`, `TimetablePeriodDef`) — a personal cross-class schedule, not just their one class-teacher section's grid.
- **Class Teacher · Students** ([lib/students.ts](lib/students.ts), [app/faculty/class/[classId]/students/page.tsx](app/faculty/class/[classId]/students/page.tsx)) — the one fully-built Class Teacher module. How it works:
  - The teacher's own class/section is resolved automatically via `subscribeToClassSectionForTeacher(schoolId, uid)` — a live query on `classSections` for `classTeacherUid == currentUid`. **No manual class picker anywhere in this flow.** If the Admin hasn't assigned this faculty as a class teacher yet, the page shows an empty state telling them to ask their Admin.
  - **Add Student** — the class teacher enters the Student ID manually (**not** auto-generated), plus: photo, name, roll no, DOB, gender, Aadhaar No, blood group, category/caste, house, admission date, previous school, address + pincode, medical history, and a Digital ID (photo or PDF upload — not a generated code). Class/section are auto-filled from the resolved `classSectionId`, not re-entered.
  - **Parent login** — exactly **one** Firebase Auth login is created per student ("Student Login": an email + password entered by the class teacher), used by whichever parent signs in — **not** one login per guardian. Father, Mother, and Guardian are plain data fields only (name, phone, occupation) with no login of their own, independent of the single Student Login. Creation goes through `createAuthUserAndRun`, writing a `users/{uid}` doc (`role: "parent"`) and the `students/{id}` doc with `guardianUids: [parentUid]` in one flow, with rollback-on-failure (see "Account deletion" below).
  - Edit/Delete/Search students, all working. Deleting a student also deletes the linked parent's Auth account.
  - Attendance/Transport are intentionally not part of this form — they're separate future modules that will populate automatically once built, not fields a class teacher fills in by hand.
- **Subject Teacher · Assignments** ([lib/assignments.ts](lib/assignments.ts), `app/faculty/subject/assignments/*`) — a Classwork/Homework diary, one entry per (class-section, subject, day) at `assignments/{classSectionId}_{subjectId}_{date}` (upsert — re-saving the same date overwrites it, not appends). `/faculty/subject/assignments` lists only the (Class · Section · Subject) slots this faculty is actually assigned to, resolved from `facultyAssignments` (see Admin section above) — not a manual picker, and not every class in the school. Each links to `/faculty/subject/assignments/[assignmentId]` (`assignmentId` == the `facultyAssignments` doc id), where the teacher enters Classwork, Homework, an optional Due Date, and an optional file attachment (photo/PDF, reuses the `schools/{schoolId}/assignments/**` Storage path), and sees their past entries for that slot below the form. Enforced by `firestore.rules`' `isSubjectTeacherOf(classSectionId, subjectId)` (a `get()` on the matching `facultyAssignments` doc) — not just hidden in the UI. **This is the one fully-built Subject Teacher module** — Students and Assessments (`app/faculty/subject/[classId]/*`) are still stubs.
- **Every other Faculty module is a stub**: Class Teacher Attendance/Assignments (a *separate*, still-unbuilt stub from the Subject Teacher one above — `app/faculty/class/[classId]/assignments`)/Achievements/Parent Requests/Leaves/Messages/Announcements, Subject Teacher Students/Assessments (`app/faculty/subject/[classId]/*`), Circulars, Events, Profile (`app/faculty/{circulars,events,profile}`) — all 5–10 line `<EmptyState>` stubs.

### Parent — Profile and Academics (Timetable) are real; everything else is a stub
- **Profile** ([app/parent/profile/page.tsx](app/parent/profile/page.tsx)) — the parent's landing page after login (see routing above). Reads the student where `guardianUids array-contains` the signed-in parent's uid via `subscribeToLinkedStudent`, and shows everything read-only: personal details, academic details (class/section/roll no/admission info), medical history, parent/guardian details, Digital ID. Access is enforced by `firestore.rules`' `isGuardianOf()` (uid membership in `guardianUids`), not just hidden in the UI — a parent's query can only ever match their own linked child. Attendance/Transport sections are explicit "Not available yet" placeholders, not faked data.
- **Academics** ([app/parent/academics/page.tsx](app/parent/academics/page.tsx)) — read-only view of their linked student's section's *published* timetable, same `timetableGrids` data Faculty see.
- **Assignments** ([app/parent/assignments/page.tsx](app/parent/assignments/page.tsx)) — read-only, reverse-chronological feed of every Classwork/Homework entry posted for their linked student's class-section, across all subjects (`subscribeToAssignmentsForSection`). This is the first Parent module that reads a *class-scoped*, not student-scoped, collection — see `parentClassLinks` below.
- **Everything else is a stub**: Dashboard, Assessments, Attendance, Achievements, Activities, Circulars, Fees, Leaves, Documents, Transport, Route Map (`app/parent/*`) — all 5-line `<EmptyState>` stubs. (Transport GPS Tracking and Route Map are meant to *stay* `EmptyState` per spec — explicitly deferred, not overlooked.)

## Account deletion / Auth cleanup

[app/api/delete-account/route.ts](app/api/delete-account/route.ts) + [lib/firebaseAdmin.ts](lib/firebaseAdmin.ts) is the only server-side code in the app. It exists because the Firebase client SDK can only delete `auth.currentUser` — never an arbitrary uid — so deleting *someone else's* login needs the Admin SDK, which only runs server-side.

- Deleting a faculty or student now also deletes the associated Firebase Auth account(s) (faculty's own login; student's linked parent login) via this route, so the email becomes reusable immediately instead of erroring with `auth/email-already-in-use` on recreation.
- [lib/secondaryAuth.ts](lib/secondaryAuth.ts)'s `createAuthUserAndRun` wraps every "create a login + a Firestore doc" flow (Admin creating a Faculty, Class Teacher creating a Student+Parent): it creates the Auth user on a *throwaway secondary Firebase app* (so the caller's own signed-in session is never replaced), then runs the Firestore writes. If those writes fail (e.g. denied by security rules), it rolls back by deleting the just-created Auth account through this same admin-authenticated route — not the client SDK's `deleteUser()` on the fresh credential, which needs a "recent login" a brand-new secondary-app session doesn't reliably have and was failing with `auth/requires-recent-login`, leaving orphaned Auth accounts behind.
- **Requires `FIREBASE_SERVICE_ACCOUNT_KEY` in `.env.local`** (a service account JSON, minified to one line) — **not yet set as of this writing**. Until it is, Firestore docs delete fine but the Auth account is orphaned, and both the delete-cleanup and the rollback-on-failure path above silently fail (logged to console, not surfaced destructively to the user).

## Data model & access control

[lib/types.ts](lib/types.ts) defines every collection's shape — including several (Attendance, Achievement, Assessment, ParentRequest, LeaveRequest, Conversation, Announcement, Circular, SchoolEvent, Activity, TransportBus, FeeStructure, StudentFee, StudentDocument) that exist only as types today, with no `lib/<name>.ts` CRUD module and no UI — placeholders for the "Flow to be executed" list below. (`Assignment`, `FacultyAssignment`, and `ParentClassLink` are no longer in that category — all three are now real, written collections, see "Subject Teacher assignment" and "Assignments" above.)

[firestore.rules](firestore.rules) is written to cover the *entire* eventual schema, not just what's built, using two extensible "bucket" registries so a new collection can get correct rules by being added to a list rather than needing a new hand-written `match` block:
1. **`isSchoolScopedAdminCollection`** — same-school read, admin-of-school write. Currently: `circulars`, `events`, `activities`, `transportBuses`, `feeStructures`, `classSections`, `facultyAssignments`, `subjects`.
2. **`isParentReviewedRequestCollection`** — parent creates a `pending` doc scoped to `(schoolId, classSectionId, studentId, parentUid)`; Class Teacher or Admin reviews it. Currently: `parentRequests`, `leaveRequests`.

Everything else (`users`, `schools`, `faculty`, `students`, `attendance`, `assignments`, `achievements`, `assessments`, `conversations`, `announcements`, `timetables`, `timetableGrids`, `studentFees`, `documents`, `parentClassLinks`) has its own explicit `match` block. Key helper functions: `isAdminOfSchool(schoolId)`, `isFacultyOfSchool(schoolId)`, `isClassTeacherOf(classSectionId)` (checks `classSections/{id}.classTeacherUid`), `isAnyTeacherOf(classSectionId)` (interim stand-in for "Subject Teacher of this section" — any faculty of the same school, until real per-subject assignment data exists), `isGuardianOf(studentId)` (uid in `guardianUids`), `isParentLinkedToClass(classSectionId)` (via the `parentClassLinks` marker doc, for class-level parent reads that aren't student-scoped — now actually populated by `lib/students.ts`'s `createStudent`/`deleteStudent`, see below; students created *before* that existed are missing the doc, which self-heals via `backfillParentClassLinks` — an unconditional overwrite (not a check-then-write; see the next gotcha) run from the Class Teacher's Student Directory page every time it loads, since only a Class Teacher/Admin has write access to `parentClassLinks`, not the parent), `isSubjectTeacherOf(classSectionId, subjectId)` (a `get()` on `facultyAssignments/{classSectionId}_{subjectId}`, checking `facultyUid` — the real per-subject counterpart to `isAnyTeacherOf`'s "any faculty of the school" placeholder, currently used only by the `assignments` collection).

[storage.rules](storage.rules) is a **separate file with its own separate publish step** (Firebase Console → Storage → Rules, distinct from Firestore Database → Rules) — it governs `schools/{schoolId}/{students,faculty,circulars,timetables,assignments,achievements}/...` upload paths, each with its own read/write helper checks mirroring the Firestore ones (`isAdminOfSchool`, `isFacultyOfSchool`, `isGuardianOfStudent`).

## Known debts / things to reconcile before building on top of them

- **`Faculty` vs `FacultyProfile` in `lib/types.ts`** — two competing Faculty schemas exist from an early merge. `Faculty` is the one actually used everywhere (`lib/faculty.ts`, the Admin Faculty page). `FacultyProfile` (with a `classSectionRoles` map) is dead — nothing writes it, and nothing in `firestore.rules` reads it anymore either — it's pure unused scaffolding, safe to delete once nothing else is expected to need it.
- **Two parallel Timetable *storage* designs still coexist**, per the comment in `firestore.rules` right above the `timetableGrids` rule: the built, section-owned `timetableGrids`/`SectionTimetable` module (above), and the original `timetables/{classSectionId}` Excel-upload design from `docs/context.md` Tab 3 (schema exists in `lib/types.ts`, rules exist, nothing built). The built module already has real Faculty/Parent read views, so this is lower-stakes than it looks — mainly matters if the Excel-upload flow is ever actually wanted; otherwise the unbuilt design can eventually just be deleted.
- **`firestore.rules` requires manual re-publish** — Firebase Console → Firestore Database → Rules → Publish. There's no CI/CD for this repo. Always the first thing to check after any local `firestore.rules` edit produces a "why can't I save/read/delete" report.
- **`storage.rules` requires its own manual re-publish — separate file, separate Firebase Console tab (Storage → Rules)**. This was the root cause of a "profile pic upload just says Saving… forever" bug for both Faculty and Student photos: `storage.rules` had very likely never been published at all (Firebase's out-of-the-box default is `allow read, write: if false` for everything), which denies every upload regardless of role. `storage.rules` now also grants Faculty (Class Teacher) write access to `schools/{schoolId}/students/{studentId}/...` (photo + Digital ID) via `isFacultyOfSchool()` — previously only Admin/Guardian could write there, which was blocking student-photo uploads independent of the publish-status issue. **Must be published before any photo/Digital ID upload will work.**
- **`isAnyTeacherOf()` is still the placeholder for *read* access** ("any faculty of the school" — used by `attendance`, `achievements`, `assessments`, `timetables`, and `assignments`' `read` rule on all of them). It's no longer the only option for *writes*, though: real per-subject assignment data now exists (`facultyAssignments`, written by Admin via `components/SubjectTeacherAssignments.tsx`), and `assignments`' `create/update/delete` rules use the real `isSubjectTeacherOf(classSectionId, subjectId)` check instead of `isAnyTeacherOf`. `assessments` still writes through the `isAnyTeacherOf` placeholder (no module built on it yet) — tighten it to `isSubjectTeacherOf` the same way once it is. (`attendance`/`achievements` writes were already tightened earlier, to `isClassTeacherOf` — unrelated to this placeholder, since those are Class Teacher actions, not Subject Teacher ones.)
- **`FIREBASE_SERVICE_ACCOUNT_KEY` is still unset** — the Auth-cleanup route exists and is wired up everywhere it's needed, but silently no-ops without this env var.

### Three Firestore-specific gotchas worth remembering (already fixed, but easy to reintroduce)

1. **`request.resource` is `null` on a Firestore `delete` operation.** A rule written as `allow create, update, delete: if ...request.resource.data...` (or `allow write: if ...`, which covers delete too) always denies deletes, since it evaluates `.data` on `null`. **Rule of thumb: `delete` rules must always read `resource.data` (the existing doc), never `request.resource.data`.** Every collection in `firestore.rules` now splits `create, update` from `delete` for this reason.
2. **Firestore validates a `list`/collection query against its entire potential result set, not its actual results** — if a security rule can't be statically proven true for every document a query's `where` clauses *could* match, the whole query is denied outright, even when every real matching document would individually pass. Concretely: `assertAdmissionNoAvailable` in `lib/students.ts` (the Student ID uniqueness check) must filter by `schoolId` **and** `classSectionId` together, matching the `list` rule's `isAnyTeacherOf(resource.data.classSectionId)` branch — filtering by `schoolId` alone silently denied the query for every class teacher regardless of what was in the collection. **If you write a new Firestore query anywhere in this app, every field the applicable security-rule branch depends on must also be pinned by an equality filter in that query**, or it'll fail with a permission error that's easy to misattribute to "rules not published."
3. **`resource` is also `null` on a `get`/`read` of a document that doesn't exist** — same underlying issue as #1 but for reads, and easy to hit the moment client code does an existence check (`getDoc` then branch on `.exists()`) against a collection whose rule unconditionally does `resource.data.something`. Hit `lib/students.ts`'s `backfillParentClassLinks` directly: it read a `parentClassLinks` doc to check whether to create it, and `parentClassLinks`' read rule threw on exactly the (nonexistent-doc) case that function existed to fix. Fixed two ways — the rule now short-circuits `resource == null` first (same pattern `timetableGrids` already used, see below), and `backfillParentClassLinks` no longer reads before writing at all (the fields are static, so an unconditional overwrite is simpler and just as correct). **If a rule's `read`/`delete` branch touches `resource.data`, either guard it with `resource == null || ...` first, or make sure nothing ever calls it against a path that might not exist.**

## Conventions to follow

- New Firestore collection: add its shape to [lib/types.ts](lib/types.ts), add its rule via the appropriate registry in [firestore.rules](firestore.rules) (or a new `match` block only if neither bucket fits), then add a `lib/<name>.ts` with the CRUD functions.
- A faculty member's "own class" is resolved via `subscribeToClassSectionForTeacher` ([lib/classSections.ts](lib/classSections.ts)) — a live query on `classSections` for `classTeacherUid == currentUid` — not a URL param, not `classSectionRoles`. Every new Class Teacher module should follow this same pattern.
- Keep using `schoolId` scoping on every school-owned document, and `classSectionId` scoping wherever `docs/context.md` describes class-level access.
- Parent → student linkage is solely `guardianUids` on the student doc; parent → class-level (non-student-scoped) reads go through the `parentClassLinks` marker doc, not a query on students.
- Deleting anything that owns a Firebase Auth login (faculty, a student's parent login) must also call `deleteAuthAccount` ([lib/secondaryAuth.ts](lib/secondaryAuth.ts), hits `/api/delete-account`) — otherwise the email is orphaned and can never be reused.
- Follow the existing page shell pattern (`Sidebar`, `Topbar`, `Modal`, `PageHeader`, `StatCard`, `DashboardCard`) already used throughout Admin/Faculty/Parent pages, for visual/UX consistency.
- If a new Firestore query's security rule depends on a field, pin that field with an equality filter in the query itself — see "Two Firestore-specific gotchas" above.
