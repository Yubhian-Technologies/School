# School ERP — Project Guide

## What this is

A multi-school ERP for Nursery–Class 10 schools, with four roles: **Super Admin**, **Admin**, **Faculty**, **Parent**. Next.js (App Router) + TypeScript + Tailwind CSS v4 + Firebase (Auth, Firestore, Storage) + one server-side API route (Firebase Admin SDK).

The full functional spec lives in [docs/context.md](docs/context.md) — treat it as the source of truth for *what* every module should eventually do. This file describes *where the project currently stands* against that spec: what's actually built and working end-to-end, what's a placeholder, how the whole app fits together, and what's known to be broken or unreconciled.

## Tech stack & architecture

- **Next.js App Router**, one route tree per role under `app/{superadmin,admin,faculty,parent}/*`, plus `app/login` and one API route (`app/api/delete-account`).
- **Firebase Auth** for login (email/password only — no self-registration; every account is created *for* someone by a higher role).
- **Firestore** for all app data, access controlled entirely by [firestore.rules](firestore.rules) (client SDK talks to Firestore directly — no data ever passes through the Next.js server, except the one delete-account route).
- **Firebase Storage** for uploaded files (photos, Digital ID docs, assignment attachments), controlled by [storage.rules](storage.rules) — a **completely separate file with its own separate publish step** in Firebase Console from `firestore.rules` (see "Known debts").
- **Firebase Admin SDK**, server-only, used by exactly one route ([app/api/delete-account/route.ts](app/api/delete-account/route.ts)) to delete an arbitrary user's Auth account — the client SDK can only ever delete `auth.currentUser`.
- No other backend. No CI/CD — both `firestore.rules` and `storage.rules` are hand-published in Firebase Console after every edit (plus `firestore.indexes.json` for any new composite index — see the Attendance bullet below for one that needs this).

## Auth & role-routing workflow (applies to every role)

1. [app/login/page.tsx](app/login/page.tsx) — a single login form (email + password) for all four roles. On success, it reads the signed-in user's `users/{uid}` Firestore doc to get their `role`, then redirects via `ROLE_HOME[role]` ([lib/roles.ts](lib/roles.ts)):
   - `superadmin` → `/superadmin/dashboard`
   - `admin` → `/admin/dashboard`
   - `faculty` → `/faculty/dashboard`
   - `parent` → `/parent/profile` (parents have no dashboard stub — Profile *is* their landing page, per spec)
2. [context/AuthContext.tsx](context/AuthContext.tsx) — app-wide, listens to `onAuthStateChanged`; whenever the Firebase Auth user changes, it fetches `users/{uid}` and exposes `{ user, profile, loading, logout, refreshProfile }` via `useAuth()`. Every page that needs the current user's `schoolId`/`role`/`name` reads it from here, not from Firebase Auth directly (the Auth user object has none of that — it all lives in the Firestore profile doc).
3. [components/RoleGuard.tsx](components/RoleGuard.tsx) — wraps each role's route group (`app/{role}/layout.tsx`, all `"use client"`), client-side redirects away if `profile.role` doesn't match the route's role, or if not signed in at all.
4. Every role's shell uses the same components for visual consistency: [components/Sidebar.tsx](components/Sidebar.tsx) (grouped nav from [lib/navigation.ts](lib/navigation.ts) — `SUPERADMIN_NAV` / `ADMIN_NAV` / `FACULTY_NAV` / `PARENT_NAV`), [components/Topbar.tsx](components/Topbar.tsx), [components/PageHeader.tsx](components/PageHeader.tsx), [components/StatCard.tsx](components/StatCard.tsx), [components/DashboardCard.tsx](components/DashboardCard.tsx), [components/Modal.tsx](components/Modal.tsx). `TopNav.tsx` no longer exists — all four roles use `Sidebar`.

**Accounts are created top-down, never self-registered:**
- Super Admin creates Admin logins (`app/superadmin/admins`).
- Admin creates Faculty logins (`app/admin/faculty`).
- A Class Teacher (Faculty) creates a Student + one Parent login together, as part of Add Student (`app/faculty/class/[classId]/students`) — see below.

## Role-by-role: what's built and how it works

### Super Admin — unchanged since project start, fully working
- **Schools** ([lib/schools.ts](lib/schools.ts), `app/superadmin/schools`) — Add/Edit/Delete schools (`name`, `place`). Every other role's data is scoped under a `schoolId`, so this is the root of the multi-tenancy model.
- **Admins** ([lib/admins.ts](lib/admins.ts), `app/superadmin/admins`) — creates an Admin login for a chosen school (email/password via the secondary-app pattern, see below), Edit/Delete.
- Dashboard + Profile pages, both simple/working.

### Admin — fully working for Faculty, Classes, Subjects, Timetable, Subject Teacher assignment, Fees, Holidays; Transport/Circulars/Events still stubs
- **Faculty** ([lib/faculty.ts](lib/faculty.ts), [app/admin/faculty/page.tsx](app/admin/faculty/page.tsx)) — full Add/Edit/Delete/Search/View. Fields: photo, name, gender, DOB, mobile, email, qualification, subjects (free text), designation, date of joining, prior experience + previous school, address, emergency contact, status (Active/Inactive). Creating a faculty member creates a real Firebase Auth login (email + password) via `createAuthUserAndRun` ([lib/secondaryAuth.ts](lib/secondaryAuth.ts)) plus a `users/{uid}` doc (`role: "faculty"`) and a `faculty/{uid}` profile doc. Deleting a faculty member deletes both Firestore docs **and** their Auth account (see "Account deletion" below), so the email becomes reusable.
- **Classes & Sections** ([lib/classSections.ts](lib/classSections.ts), [components/ClassSectionsManager.tsx](components/ClassSectionsManager.tsx), `app/admin/classes/*`) — Admin picks a class from a fixed Nursery→Class 10 list ([lib/classes.ts](lib/classes.ts)), adds one or more sections to it (e.g. "A", "B"), and assigns **one faculty member as `classTeacherUid`** per section — a faculty can be class teacher of only one section at a time (`assertTeacherAvailable` enforces this both on create and on reassignment). **This is the single, real, populated source of "who teaches which class" app-wide** — every other module (Student Directory, Attendance, Timetable, Faculty Dashboard) resolves "my class" from `classSections.classTeacherUid`, never from a manual picker or URL param. Deleting a section also deletes its `timetableGrids/{id}` doc.
- **Subjects** ([lib/subjects.ts](lib/subjects.ts), `app/admin/subjects/page.tsx`) — a per-class subject catalog (Nursery–Class 10), shared across all sections of a class (a subject isn't section-specific — all of Class 5-A/B/C study the same subjects). Fields: Name, Code, Type (Theory/Practical/Activity), Hours/Week. Add/Edit/Delete via one modal; class picked via a dropdown on the page itself.
- **Timetable** ([lib/timetableGrid.ts](lib/timetableGrid.ts), `components/timetable/*`, `app/admin/timetable/*`) — per-section, not shared: every `classSections/{id}` owns one independent `timetableGrids/{id}` doc (own days/periods/breaks/cells, `draft`/`published` status). Clicking "Create Timetable" auto-generates a default Mon–Sat × Period 1–8 grid with a Lunch Break rather than starting blank; "Edit Structure" customizes days/periods/breaks after. Cells hold subject/faculty/room/notes, edited via a dialog — Subject is picked from that class's real Subject catalog (not free text), there's no custom cell-color picker (every cell renders the same default look), and consecutive periods with the same subject in one day column are visually merged into a single spanning cell (display-only — each period still has its own independent `cells` entry). A timetable must be explicitly **published** before Faculty/Parent can see it. Sections are read straight from the real `classSections` collection (no separate section-picker collection).
- **Holidays** ([lib/holidays.ts](lib/holidays.ts), `app/admin/holidays/page.tsx`) — Admin declares Full-Day or Half-Day holidays (public holidays, vacations, sudden/emergency closures) for the **whole school**, via a click-a-date calendar UI (one `holidays/{schoolId}_{date}` doc per date; re-declaring the same date overwrites it — unlike Attendance, holidays are also **deletable**, not just editable). Every Sunday is a holiday by default at the application level (`isDefaultHoliday`) with no stored doc needed. Faculty's Attendance Dashboard/Take Attendance pages read this read-only to skip a cancelled session — Class Teachers can no longer declare holidays themselves (an earlier per-class design was superseded by this school-wide one).
- **Subject Teacher assignment** ([lib/facultyAssignments.ts](lib/facultyAssignments.ts), [components/FacultySubjectAssignments.tsx](components/FacultySubjectAssignments.tsx)) — surfaced from the **Faculty page**, not Classes & Sections: a "Subjects" action on each faculty row (also in the View Faculty modal) opens a per-faculty modal where the Admin picks Class → Section → Subject and adds it to that faculty's list of assignments (with a list of their current ones, each removable). Writes `facultyAssignments/{classSectionId}_{subjectId}` docs (`role: "SUBJECT_TEACHER"`) — the real, populated source of "who teaches what where" for Subject Teachers, the counterpart to `classSections.classTeacherUid` for Class Teachers, and what filters which classes a Subject Teacher can post Assignments for (see below). Deliberately keyed from the faculty side (not the section side) — picking a faculty member first, then their classes/subjects, was the requested flow.
- **Fees** ([lib/feeStructures.ts](lib/feeStructures.ts), [lib/studentFees.ts](lib/studentFees.ts), `app/admin/fees/*`, [components/fees/ClassFeeStructureManager.tsx](components/fees/ClassFeeStructureManager.tsx), [components/fees/StudentFeeDetailModal.tsx](components/fees/StudentFeeDetailModal.tsx)) — two layers: a per-class fee structure (`/admin/fees/[classId]`, admission/tuition/books/uniform/transport/other charges, tuition defaulting from `DEFAULT_TUITION_FEE_BY_CLASS_ID`) shared by every section of that class (same pattern as Subjects), and a per-student discount-percentage override (`StudentFeeDetailModal`) that computes that student's actual payable/paid/due against the class structure. `studentFees` is treated as sensitive (guardian-only + admin, unlike the class-level `feeStructures`).
- **Transport, Circulars, Events** — `app/admin/{transport,circulars,events}/page.tsx` are all 5-line `<EmptyState>` stubs. Nothing built yet.

### Faculty — Dashboard, Timetable, Class Teacher Students/Attendance, and Subject Teacher Assignments are real; everything else is a stub
- **Dashboard** ([app/faculty/dashboard/page.tsx](app/faculty/dashboard/page.tsx)) — welcome header, stat cards (own class + student count, resolved live via `subscribeToClassSectionForTeacher`), and grouped quick-link cards for every Class Teacher / Subject Teacher / General module (most of which route through to stubs today, but the dashboard itself is complete).
- **Timetable** (`app/faculty/timetable/*`) — a real, read-only view of a section's *published* `timetableGrids` doc. Faculty browse to their own class-teacher section or any other section within the school; drafts are invisible to them (enforced by `firestore.rules`, not just hidden in the UI). Also includes **"My Timetable"** ([components/timetable/MyFacultyTimetable.tsx](components/timetable/MyFacultyTimetable.tsx)) — every period this faculty member is assigned to (as the cell's `facultyId`) across *all* published sections/classes in the school, merged and sorted in time order using each period's optional `startTime`/`endTime` (`lib/timetableGrid.ts`, `TimetablePeriodDef`) — a personal cross-class schedule, not just their one class-teacher section's grid.
- **Class Teacher · Students** ([lib/students.ts](lib/students.ts), [app/faculty/class/[classId]/students/page.tsx](app/faculty/class/[classId]/students/page.tsx)) — the teacher's own class/section is resolved automatically via `subscribeToClassSectionForTeacher(schoolId, uid)` — a live query on `classSections` for `classTeacherUid == currentUid`. **No manual class picker anywhere in this flow.** If the Admin hasn't assigned this faculty as a class teacher yet, the page shows an empty state telling them to ask their Admin.
  - **Add Student** — the class teacher enters the Student ID manually (**not** auto-generated), plus: photo, name, roll no, DOB, gender, Aadhaar No, blood group, category/caste, house, admission date, previous school, address + pincode, medical history, and a Digital ID (photo or PDF upload — not a generated code). Class/section are auto-filled from the resolved `classSectionId`, not re-entered.
  - **Parent login** — exactly **one** Firebase Auth login is created per student ("Student Login": an email + password entered by the class teacher), used by whichever parent signs in — **not** one login per guardian. Father, Mother, and Guardian are plain data fields only (name, phone, occupation) with no login of their own, independent of the single Student Login. Creation goes through `createAuthUserAndRun`, writing a `users/{uid}` doc (`role: "parent"`), the `students/{id}` doc with `guardianUids: [parentUid]`, and a `parentClassLinks/{parentUid}_{classSectionId}` marker doc (lets that parent read class-scoped collections like Assignments — see below), all in one flow with rollback-on-failure (see "Account deletion" below).
  - Edit/Delete/Search students, all working. Deleting a student also deletes the linked parent's Auth account and their `parentClassLinks` doc.
  - Every time this page loads, it also self-heals `parentClassLinks` for students created before that doc existed, via `backfillParentClassLinks` — see the Firestore gotchas below for why this matters.
- **Class Teacher · Attendance** ([lib/attendance.ts](lib/attendance.ts), `app/faculty/class/[classId]/attendance/*`, [components/attendance/AttendanceDateDetail.tsx](components/attendance/AttendanceDateDetail.tsx)) — Morning and Afternoon are two fully independent submissions (see `AttendanceSession` in [lib/types.ts](lib/types.ts)): a Present/Absent checkbox per active student per session, live totals, blocks save until every student is resolved. Take Attendance now has a real date picker (any date up to today, no floor — see that file for the tradeoff) instead of being locked to today; picking a date that already has a submitted session **loads its existing per-student statuses and opens it in an edit state** rather than blocking re-entry, and saving again upserts (overwrites) it. The Dashboard's "Take/Edit Attendance" link and the History list's new "Edit" action (next to the existing read-only "View") both route into this same flow, "Edit" pre-filling the date via a `?date=` query param. Two collections are written together in one `writeBatch` per submission: the per-student `attendance/{studentId}_{date}_{session}` doc (source of truth parents read directly, scoped by `isGuardianOf`) and `attendanceSummaries/{classSectionId}_{date}_{session}` (class-teacher-only, never read by parents) — deliberately **not** a single doc-per-class-with-a-`students[]`-array design, since that shape would let one guardian's read access leak every classmate's status (Firestore rules are document-level, not per-array-element). `firestore.rules` allows both `create` **and** `update` for the real Class Teacher on both collections — `delete` stays `if false` always; a record can be corrected, never removed (see "Known debts" for exactly what this does and doesn't enforce). Also read-only by **Admin**, via the same Classes → Sections drill-down pattern as `app/admin/classes`/`app/admin/timetable`: `app/admin/attendance` is a Class grid ([components/attendance/AttendanceClassSections.tsx](components/attendance/AttendanceClassSections.tsx) then lists that class's Sections), and picking a Section opens [components/attendance/AttendanceSectionMonthView.tsx](components/attendance/AttendanceSectionMonthView.tsx) — a Month/Year-dropdown history table (shared with the Faculty Dashboard's History section via [components/attendance/AttendanceMonthTable.tsx](components/attendance/AttendanceMonthTable.tsx)'s `buildMonthHistoryRows`/`MonthYearPicker`) whose "View" action reuses `AttendanceDateDetail` via its optional `section`/`backHref` props rather than that component's default self-resolve-my-own-class behavior. Admin has no write access to either collection. `subscribeToAttendanceHistory` (`lib/attendance.ts`) takes `schoolId` as well as `classSectionId` — both are now pinned by equality filters since the query is read by two different rule branches (Faculty's `isAnyTeacherOf`, Admin's `isAdminOfSchool`), and only pinning `classSectionId` left the Admin `list` unprovable (same gotcha class as #2 below). Needs the `attendanceSummaries` composite index (`schoolId` + `classSectionId` + `date`) in `firestore.indexes.json` deployed/created (see "Flow to be executed").
- **Subject Teacher · Assignments** ([lib/assignments.ts](lib/assignments.ts), `app/faculty/subject/assignments/*`) — a Classwork/Homework diary, one entry per (class-section, subject, day) at `assignments/{classSectionId}_{subjectId}_{date}` (upsert — re-saving the same date overwrites it, not appends). `/faculty/subject/assignments` lists only the (Class · Section · Subject) slots this faculty is actually assigned to, resolved from `facultyAssignments` (see Admin section above) — not a manual picker, and not every class in the school. Each links to `/faculty/subject/assignments/[assignmentId]` (`assignmentId` == the `facultyAssignments` doc id), where the teacher enters Classwork, Homework, an optional Due Date, and an optional file attachment (photo/PDF, reuses the `schools/{schoolId}/assignments/**` Storage path), and sees their past entries for that slot below the form. Enforced by `firestore.rules`' `isSubjectTeacherOf(classSectionId, subjectId)` (a `get()` on the matching `facultyAssignments` doc) — not just hidden in the UI. **This is the one fully-built Subject Teacher module** — Students and Assessments (`app/faculty/subject/[classId]/*`) are still stubs.
- **Every other Faculty module is a stub**: Class Teacher Assignments (a *separate*, still-unbuilt stub from the Subject Teacher one above — `app/faculty/class/[classId]/assignments`)/Achievements/Parent Requests/Leaves/Messages/Announcements, Subject Teacher Students/Assessments (`app/faculty/subject/[classId]/*`), Circulars, Events, Profile (`app/faculty/{circulars,events,profile}`) — all 5–10 line `<EmptyState>` stubs.

## Account deletion / Auth cleanup

[app/api/delete-account/route.ts](app/api/delete-account/route.ts) + [lib/firebaseAdmin.ts](lib/firebaseAdmin.ts) is the only server-side code in the app. It exists because the Firebase client SDK can only delete `auth.currentUser` — never an arbitrary uid — so deleting *someone else's* login needs the Admin SDK, which only runs server-side.

- Deleting a faculty or student now also deletes the associated Firebase Auth account(s) (faculty's own login; student's linked parent login) via this route, so the email becomes reusable immediately instead of erroring with `auth/email-already-in-use` on recreation.
- [lib/secondaryAuth.ts](lib/secondaryAuth.ts)'s `createAuthUserAndRun` wraps every "create a login + a Firestore doc" flow (Admin creating a Faculty, Class Teacher creating a Student+Parent): it creates the Auth user on a *throwaway secondary Firebase app* (so the caller's own signed-in session is never replaced), then runs the Firestore writes. If those writes fail (e.g. denied by security rules), it rolls back by deleting the just-created Auth account through this same admin-authenticated route — not the client SDK's `deleteUser()` on the fresh credential, which needs a "recent login" a brand-new secondary-app session doesn't reliably have and was failing with `auth/requires-recent-login`, leaving orphaned Auth accounts behind.
- **`FIREBASE_SERVICE_ACCOUNT_KEY` is now set in `.env.local`** (a service account JSON, minified to one line) — this Auth cleanup path should now actually work end-to-end locally. Note this service account is scoped narrowly (Admin SDK data operations only — it does **not** have IAM permission to deploy Firestore/Storage rules; that was confirmed the hard way when a CLI-deploy attempt hit a 403 on `serviceusage.googleapis.com`, so rules publishing still has to go through the Firebase Console). If this app is ever deployed anywhere beyond local dev, confirm the same env var is configured there too.

## Data model & access control

[lib/types.ts](lib/types.ts) defines every collection's shape — including several (Achievement, ParentRequest, LeaveRequest, Conversation, Announcement, Circular, SchoolEvent, Activity, TransportBus, StudentDocument, Assessment, AcademicRecord, Holiday, DocumentRequirement) that exist only as types + rules today, with no `lib/<name>.ts` CRUD module and no UI yet — placeholders for the "Flow to be executed" list below. (`Assignment`, `FacultyAssignment`, `ParentClassLink`, `AttendanceRecord`/`AttendanceSummary`, `FeeStructure`, and `StudentFee` are no longer in that category — all are now real, written collections, see the role sections above.) `Assessment` was redefined (class-scoped quiz/competition, not per-student marks) once `AcademicRecord` was added as the separate per-student exam-marks concept — see both types' doc comments.

**Holidays are Admin-owned and school-wide** (`Holiday`, `holidays/{schoolId}_{date}`) — a public holiday, vacation, or emergency closure the Admin declares for the *entire school*, not per class-section. This superseded an earlier per-Class-Teacher design (`attendanceHolidays/{classSectionId}_{date}`, since removed) once the actual requirement turned out to be school-wide admin policy, not something each Class Teacher should own individually. Every Sunday is treated as a holiday by default at the application level ([lib/holidays.ts](lib/holidays.ts)'s `isDefaultHoliday`) without a stored doc — a `holidays` doc is only for exceptions or default-overrides. Faculty's Attendance Dashboard/Take Attendance pages already read this (read-only) to skip a cancelled session; the Admin's own calendar UI is `app/admin/holidays/page.tsx` (click any date to declare/edit/remove a Full-Day or Half-Day holiday with a reason — Sundays show as holidays automatically without needing a click). `holidays` deliberately has its *own* `match` block rather than living in the `isSchoolScopedAdminCollection` bucket below, even though the permission shape matches — see the "Firestore gotchas" note: its read rule needs *two* OR'd branches (an id-parsed one for Take Attendance's direct `get()` on today's — usually nonexistent — holiday doc, and a `resource.data`-based one for the Admin Holidays calendar's ranged `list` query), and the shared bucket only ever had the single resource.data-based shape, never the id-parsed one.

[firestore.rules](firestore.rules) is written to cover the *entire* eventual schema, not just what's built, using two extensible "bucket" registries so a new collection can get correct rules by being added to a list rather than needing a new hand-written `match` block:
1. **`isSchoolScopedAdminCollection`** — same-school read, admin-of-school write. Currently: `circulars`, `events`, `activities`, `transportBuses`, `feeStructures`, `classSections`, `facultyAssignments`, `subjects`. Only safe for a collection that's never read via a direct `get()` on a doc id that might not exist (see `holidays` above for why that's a real trap, not a hypothetical one).
2. **`isParentReviewedRequestCollection`** — parent creates a `pending` doc scoped to `(schoolId, classSectionId, studentId, parentUid)`; Class Teacher or Admin reviews it. Currently: `parentRequests`, `leaveRequests`.

Everything else (`users`, `schools`, `faculty`, `students`, `attendance`, `attendanceSummaries`, `assignments`, `achievements`, `assessments`, `academicRecords`, `conversations`, `announcements`, `timetables`, `timetableGrids`, `studentFees`, `documents`, `documentRequirements`, `parentClassLinks`) has its own explicit `match` block. Key helper functions: `isAdminOfSchool(schoolId)`, `isFacultyOfSchool(schoolId)`, `isClassTeacherOf(classSectionId)` (checks `classSections/{id}.classTeacherUid`), `isAnyTeacherOf(classSectionId)` (interim stand-in for "any teacher of this section" — any faculty of the same school, still used for several collections' *read* rules), `isSubjectTeacherOf(classSectionId, subjectId)` (a `get()` on `facultyAssignments/{classSectionId}_{subjectId}`, checking `facultyUid` — the real per-subject counterpart to `isAnyTeacherOf`, used by `assignments`/`assessments`/`academicRecords`' write rules), `isGuardianOf(studentId)` (uid in `guardianUids`), `isParentLinkedToClass(classSectionId)` (via the `parentClassLinks` marker doc, for class-level parent reads that aren't student-scoped — populated by `lib/students.ts`'s `createStudent`/`deleteStudent`, plus self-healed for pre-existing students by `backfillParentClassLinks`, see the gotchas below).

`studentFees` write access now also includes the real Class Teacher of that student's section (`isClassTeacherOf`), not just Admin — the intended flow is Admin sets the class-wide `feeStructures` default, and the Class Teacher may then adjust an individual student's negotiated discount/payable.

[storage.rules](storage.rules) is a **separate file with its own separate publish step** (Firebase Console → Storage → Rules, distinct from Firestore Database → Rules) — it governs `schools/{schoolId}/{students,faculty,circulars,timetables,assignments,achievements,events}/...` upload paths, each with its own read/write helper checks mirroring the Firestore ones (`isAdminOfSchool`, `isFacultyOfSchool`, `isGuardianOfStudent`). The upload size cap (`isReasonableUpload()`) was raised from 10MB to 20MB — modern phone-camera photos routinely exceed 10MB, and a rejected upload from that cap looks exactly like a generic "Firebase error" to a user with no obvious cause.

## Known debts / things to reconcile before building on top of them

- **`Faculty` vs `FacultyProfile` in `lib/types.ts`** — two competing Faculty schemas exist from an early merge. `Faculty` is the one actually used everywhere (`lib/faculty.ts`, the Admin Faculty page). `FacultyProfile` (with a `classSectionRoles` map) is dead — nothing writes it, and nothing in `firestore.rules` reads it anymore either — it's pure unused scaffolding, safe to delete once nothing else is expected to need it.
- **Two parallel Timetable *storage* designs still coexist**, per the comment in `firestore.rules` right above the `timetableGrids` rule: the built, section-owned `timetableGrids`/`SectionTimetable` module, and the original `timetables/{classSectionId}` Excel-upload design from `docs/context.md` Tab 3 (schema exists in `lib/types.ts`, rules exist, nothing built). The built module already has real Faculty/Parent read views, so this is lower-stakes than it looks — mainly matters if the Excel-upload flow is ever actually wanted; otherwise the unbuilt design can eventually just be deleted.
- **`firestore.rules` requires manual re-publish** — Firebase Console → Firestore Database → Rules → Publish. There's no CI/CD for this repo, and the service account in `.env.local` can't be used to script around this (see "Account deletion" above — it lacks the IAM role). Always the first thing to check after any local `firestore.rules` edit produces a "why can't I save/read/delete" report — and when re-checking, paste the **entire** file fresh into the Console rather than editing around the existing text, to rule out a stale/partial paste.
- **`storage.rules` requires its own manual re-publish — separate file, separate Firebase Console tab (Storage → Rules)**. Grants Faculty (Class Teacher) write access to `schools/{schoolId}/students/{studentId}/...` (photo + Digital ID) via `isFacultyOfSchool()`, on top of Admin/Guardian.
- **Attendance is no longer immutable, and dates still aren't validated server-side.** Take Attendance ([app/faculty/class/[classId]/attendance/take](app/faculty/class/[classId]/attendance/take/page.tsx)) now has a real date picker (any date up to and including today — no floor on how far back, see the tradeoff note in that file) and a real edit flow: selecting a date that already has a submitted session loads its existing per-student statuses and lets the Class Teacher correct and re-save it, rather than blocking re-entry. `attendance/{id}` and `attendanceSummaries/{id}`'s rules now allow `update` (by the real `isClassTeacherOf`, checked against `resource.data` — the existing doc — not `request.resource.data`), not just `create`; `delete` is still `if false` for both, always. [lib/attendance.ts](lib/attendance.ts)'s `submitSessionAttendance` upserts: a plain (non-batched) read of the summary doc decides fresh-create vs edit, `createdAt`/`submittedAt` is stamped once and preserved, `updatedAt` is stamped on every edit, and every write uses `{ merge: true }` so an edit doesn't clobber the original creation timestamp (a cleared remark is explicitly `deleteField()`'d, since merge alone wouldn't remove it). Neither `create` nor `update` verify *which* date a write targets server-side (still deliberately skipped — timezone-aware date arithmetic in Rules is easy to get subtly wrong) — this doesn't change the risk surface from before: a modified client could already submit an arbitrary date once; it can now also edit whatever date it already wrote, which is the same legitimate use case the real UI now exposes on purpose. Admin has **read-only** access to both collections (`isAdminOfSchool`, unchanged) — no write access was added for Admin.
- **`isAnyTeacherOf()` is still the placeholder for *read* access** on several collections ("any faculty of the school" — `achievements`, `timetables`, and `assignments`' `read` rule). Writes have been tightened collection-by-collection as each was actually built: `attendance`/`attendanceSummaries` and `achievements` write through the real `isClassTeacherOf`; `assignments`, `assessments`, and `academicRecords` all write through the real `isSubjectTeacherOf`.

### Three Firestore-specific gotchas worth remembering (already fixed, but easy to reintroduce)

1. **`request.resource` is `null` on a Firestore `delete` operation.** A rule written as `allow create, update, delete: if ...request.resource.data...` (or `allow write: if ...`, which covers delete too) always denies deletes, since it evaluates `.data` on `null`. **Rule of thumb: `delete` rules must always read `resource.data` (the existing doc), never `request.resource.data`.** Every collection in `firestore.rules` now splits `create, update` from `delete` for this reason.
2. **Firestore validates a `list`/collection query against its entire potential result set, not its actual results** — if a security rule can't be statically proven true for every document a query's `where` clauses *could* match, the whole query is denied outright, even when every real matching document would individually pass. Concretely: `assertAdmissionNoAvailable` in `lib/students.ts` (the Student ID uniqueness check) must filter by `schoolId` **and** `classSectionId` together, matching the `list` rule's `isAnyTeacherOf(resource.data.classSectionId)` branch — filtering by `schoolId` alone silently denied the query for every class teacher regardless of what was in the collection. **If you write a new Firestore query anywhere in this app, every field the applicable security-rule branch depends on must also be pinned by an equality filter in that query**, or it'll fail with a permission error that's easy to misattribute to "rules not published." (Same principle applies to any *new composite index* a query needs — `attendanceSummaries`' history query needs one in `firestore.indexes.json`; a missing index looks exactly like a rules problem but isn't one.)
3. **`resource` is also `null` on a `get`/`read` of a document that doesn't exist** — same underlying issue as #1 but for reads, and easy to hit the moment client code does an existence check (`getDoc` then branch on `.exists()`) against a collection whose rule unconditionally does `resource.data.something`. Hit `lib/students.ts`'s `backfillParentClassLinks` directly: it read a `parentClassLinks` doc to check whether to create it, and `parentClassLinks`' read rule threw on exactly the (nonexistent-doc) case that function existed to fix. Fixed two ways — the rule now short-circuits `resource == null` first (same pattern `timetableGrids` and `attendanceSummaries` already use), and `backfillParentClassLinks` no longer reads before writing at all (the fields are static, so an unconditional overwrite is simpler and just as correct). **If a rule's `read`/`delete` branch touches `resource.data`, either guard it with `resource == null || ...` first, or make sure nothing ever calls it against a path that might not exist.** Recurred (twice) with `holidays`: first added to the `isSchoolScopedAdminCollection` bucket, which denied Take Attendance's daily `get()` on (usually nonexistent) today's holiday outright, since that bucket's read rule only ever had the resource.data-based shape. Fixed by moving `holidays` to its own dedicated block with an id-parsed branch alongside — but that *alone* then broke the Admin Holidays calendar's ranged `list` query, because (per gotcha #2 above) a check based on the document id can't be correlated with a query's field-equality filter, so `list` needs its own resource.data-based branch too — the final `holidays` rule needs **both** branches simultaneously, exactly like `attendanceSummaries`. A tempting-but-wrong "fix" along the way was adding a `resource == null` fallback to the *shared bucket-1 rule itself* (to also cover `feeStructures`, which has the same latent gotcha, silently masked by an `onSnapshot` error callback that treats any error as "not set up yet") — reverted without shipping it, since that bucket backs `list` queries everywhere (Subjects, Classes & Sections, facultyAssignments, Transport...) and there was no way to confirm in this environment (no live Firestore rules simulator) that mixing a null-resource branch into an already-list-provable rule doesn't break the provability check for every existing member. **Never touch a rule that many active `list` queries depend on without being able to verify the change; give the one collection that actually needs different behavior its own dedicated block instead, however small.**

## Conventions to follow

- New Firestore collection: add its shape to [lib/types.ts](lib/types.ts), add its rule via the appropriate registry in [firestore.rules](firestore.rules) (or a new `match` block only if neither bucket fits), then add a `lib/<name>.ts` with the CRUD functions.
- A faculty member's "own class" is resolved via `subscribeToClassSectionForTeacher` ([lib/classSections.ts](lib/classSections.ts)) — a live query on `classSections` for `classTeacherUid == currentUid` — not a URL param, not `classSectionRoles`. Every new Class Teacher module should follow this same pattern.
- Keep using `schoolId` scoping on every school-owned document, and `classSectionId` scoping wherever `docs/context.md` describes class-level access.
- Parent → student linkage is solely `guardianUids` on the student doc; parent → class-level (non-student-scoped) reads go through the `parentClassLinks` marker doc, not a query on students.
- Deleting anything that owns a Firebase Auth login (faculty, a student's parent login) must also call `deleteAuthAccount` ([lib/secondaryAuth.ts](lib/secondaryAuth.ts), hits `/api/delete-account`) — otherwise the email is orphaned and can never be reused.
- Follow the existing page shell pattern (`Sidebar`, `Topbar`, `Modal`, `PageHeader`, `StatCard`, `DashboardCard`) already used throughout Admin/Faculty/Parent pages, for visual/UX consistency.
- If a new Firestore query's security rule depends on a field, pin that field with an equality filter in the query itself — see "Three Firestore-specific gotchas" above.
- If a record should never be editable once created (e.g. Attendance), enforce that in `firestore.rules` itself (`allow update, delete: if false`) — don't rely on the UI simply not offering an edit affordance.
